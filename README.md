# Keitaro Wrapper

Веб-обёртка над Keitaro Admin API v1: создание кампаний и безопасное редактирование офферов
с локальными черновиками, публикацией и архивом.

FastAPI · SQLAlchemy 2.0 · PostgreSQL · Alembic · httpx · HTML/JS.

## Запуск (Windows, PowerShell)

```powershell
cd C:\Users\MSI\keitaro_wrapper
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
copy .env.example .env        # впишите пароль БД и API-ключ Keitaro
alembic upgrade head          # создаёт таблицы
uvicorn app.main:app --reload
```

Откройте http://127.0.0.1:8000 (Swagger: /docs).

Если в папке уже есть старая папка `alembic/` и миграции от прошлых попыток - сохраните их в
сторонку: этот проект содержит свою `alembic/versions/0001_initial.py`.
Если вы уже применяли другую миграцию к базе `keitaro_wrapper`, проще пересоздать пустую БД.

### Важно: предохранитель записи
`KEITARO_WRITE_ENABLED=false` по умолчанию. Пока он выключен, обёртка **только читает** Keitaro:
создание кампании и Push возвращают 403. Включайте (`true`) осознанно, лучше сначала на тестовой кампании.

## Как это устроено

### Две копии состояния
У каждой привязки «оффер в потоке» (`stream_offers`) есть `published_*` (что в Keitaro) и `draft_*`
(что хочет пользователь). Все кнопки меняют только `draft_*`. Поток **dirty**, если у какой-то
привязки draft != published. Флаг dirty не хранится, а вычисляется (`services/domain.py:is_dirty`),
поэтому он не может разойтись с данными.

| published_state | draft_state | Значение |
|---|---|---|
| NULL | active | добавлен локально, в Keitaro не публиковался |
| active | active (доля та же) | чисто |
| active | removed | удалён в черновике, при Push уйдёт из Keitaro |
| removed | removed | архив |
| removed | active | Bring back |

### Слои
- `services/domain.py` - **чистая** логика (доли, dirty, cancel, слияние при синхронизации), без БД и HTTP; покрыта тестами.
- `services/drafts.py` - операции add / remove / restore / pin / cancel. Меняют draft, пересчитывают доли, пишут историю.
- `services/sync.py` - Keitaro -> локальная БД (только чтение).
- `services/publish.py` - Push.
- `services/campaigns.py` - создание кампании.
- `keitaro/client.py` - httpx-клиент; запись возможна только через `write=True` + настройку.

### Доли
При удалении оффера его закрепление сбрасывается (доля у удалённого 0%); после Bring back он снова незакреплённый.

Закреплённые сохраняют долю, остаток делится поровну между незакреплёнными, остаток от деления
отдаётся первым (75% на двоих -> 38 и 37). Сумма активных всегда ровно 100. Если все закреплены и сумма
не 100, или закреплено слишком много - ошибка 400, ничего не меняется.

### Синхронизация
При открытии кампании и по кнопке **Fetch Streams** (`GET /api/campaigns/{id}`) потоки и офферы подтягиваются из Keitaro.
Потоки без офферов добавляются как обычные потоки: их содержимое (редирект, фильтры) не разбирается и не показывается.
- Оффер удалили в Keitaro мимо обёртки -> привязка **не удаляется**, помечается removed (архив), доступна Bring back.
- Поток исчез из Keitaro -> `remote_deleted=true`.
- Неопубликованный черновик не затирается; обновляются только `published_*`.

### Публикация и частичные сбои
Единица публикации - один поток (один `PUT /streams/{id}`). `published_*` пишутся в БД только после
успешного ответа Keitaro. Ошибка в потоке не помечается успехом, поток остаётся dirty; остальные
публикуются, ответ содержит статус по каждому потоку (`published` / `error` / `unchanged`).
Если Keitaro принял запрос, а БД не сохранила - следующая синхронизация восстановит картину.

### Создание кампании
Все ID (оффер, домен, группа, источник) проверяются до записи. Затем: кампания -> поток GEO (regular,
country accept, HTTP redirect на google) -> default-поток с оффером 100%. Если default-поток в кампании
уже есть, он обновляется, а не создаётся второй. Локальная запись кампании сохраняется сразу после
создания в Keitaro, чтобы не потерять её при сбое на потоках.

## Что нужно сверить с вашим Keitaro (Swagger: https://tlgk.host/admin)
Эти места написаны по вашему описанию и документации, но не проверялись на живом API:
1. Поля `POST /streams`: `schema` для GEO-потока (`action`) и для потока с офферами (`landings`) - константы в `services/campaigns.py`.
2. `PUT /streams/{id}` с одним полем `offers` (если Keitaro требует полный объект - дополнить `build_offers_payload`).
3. Содержит ли ответ `GET /campaigns/{id}/streams` поле `offers` у потока и поля `offer_id`, `share`, `state`, `id` (`services/sync.py`).
4. Поля стоимости кампании (CPC и т.п.) в `POST /campaigns` не передаются - добавьте в `services/campaigns.py`, если они обязательны.

5. Поиск офферов (`GET /api/keitaro/offers?q=`) фильтрует список `GET /offers` на нашей стороне по ID или части названия.
